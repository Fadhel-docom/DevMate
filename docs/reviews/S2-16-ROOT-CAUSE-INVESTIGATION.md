## 1. What the code does

| Question | Evidence |
|---|---|
| One lock name for every mutator? | `STORAGE_LOCK_NAME = "devmate-workspace-v1"` (`storage.ts:8`). The only `navigator.locks.request` call in `src/` (non-test) is inside `withStorageLock` (`storage.ts:263`). `saveProjectsLocked` (284-287), `readProjectsLocked` (288-296), `restoreBackup` (324-), `deleteBackup` (376-) call `withStorageLock`; `cutoverController.ts:142` and `durableStore.ts:103` also go through `withStorageLock`. So compare and write are inside one lock hold. **But** `expectedRaw` itself comes from an earlier, separate lock hold: `App.tsx:100-104` (`readProjectsLocked` → `baselineRaw.current`) and `App.tsx:130-131` (`baselineRaw.current = result.raw` after the tab's own successful save). |
| Paths that write `STORAGE_KEY` | `saveProjects` (`storage.ts:211`), `restoreBackup` (347, rollback 357/360), plus `readProjects` → `backUpRaw` writes backup slots only. `durableStore.ts` and `cutoverController.ts` read `STORAGE_KEY` (`durableStore.ts:409`, `cutoverController.ts:146,357`) and do not write it. Unlocked exported `saveProjects` (192) and `readProjects` (161) exist; the app reaches storage only through the `*Locked` wrappers (`App.tsx:100,130,153`; `BackupManager.tsx:47,61`). `readProjectsLocked` falls back to an unlocked read when Web Locks is absent (291-294); `saveProjectsLocked` then fails with `lock-unavailable` instead of writing. |
| Timeout / abort / race | `withStorageLock` (257-280): `AbortController` plus `Promise.race([work, timeout])`; the timer is cleared as the first statement of the lock callback (264), so the timeout cannot fire after the callback has started *running*. Residual window (code reading only, **not reproduced**): if the timer task runs after the lock was granted but before the callback task runs, `abort()` is a no-op (the request already succeeded), the caller receives `lock-timeout` and the callback still executes later and may write. S2-16 never produced `lock-timeout` (only `ok` and `conflict`), so this is not involved in S2-16. |

## 2. How two tabs used the same `expectedRaw` and both succeeded (instrumented, real code)

For every trial the harness logged, per tab, lock-granted, each `getItem(STORAGE_KEY)` result (classified `baseline` / `own-write` / `other-tab-write`), the `setItem`, and lock-callback-done.

- **60-trial run (hold 0, real `saveProjectsLocked`):** 35 trials ended with both tabs `ok` (and one acknowledged edit missing in each: 35). Locks were serialised in every trial by the timestamps (first callback finished 0 to 1.8 ms before the second grant). In **all 35** both-ok trials the second tab's compare read **inside its own lock** returned `baseline`, although the first tab had already completed its `setItem` (34 of 35 with a strictly positive interval; 1 had the same 0.1 ms timestamp). In the 25 trials that produced `conflict`, the second tab's compare read returned the other tab's write (25/25). A second run (40 trials) gave 20 both-ok, 20/20 with a `baseline` compare read; in one of those trials the two lock intervals overlap by 0.1 ms, which is the resolution/skew of per-page `performance.timeOrigin` timestamps, not evidence of lock overlap (the other 39 are strictly ordered).
- **Cause (proven by observation):** the lock serialises the *critical sections*, but a `localStorage.setItem` in tab A is not yet visible to `localStorage.getItem` in tab B when B is granted the lock a fraction of a millisecond later. B compares a stale value equal to the old baseline, passes `expectedRaw`, and `setItem` overwrites A's data. This is the same mechanism measured in S2-02 (stale null marker read after the other tab's write) and S2-04 (counter).
- **Not proven:** Chromium's internal reason (browser-process propagation delay of the DOMStorage cache is the likely mechanism, but it was not instrumented at that level), and any guarantee about other browsers. Only the observable behaviour in Chromium 153 is proven.
- **Mitigation experiment (diagnostic variant, NOT production code):** same test but the lock callback keeps the lock for H ms after `saveProjects`. Results, 40 trials each: H=0 → 20 both-ok; **H=5 → 0, H=25 → 0, H=100 → 0** (0 of 120 trials lost an update). Strongly supports the visibility-delay explanation; it is a timing heuristic on this host, not a guarantee.

## 3. Comparison with S2-16

S2-16 (A) 15/40 both-ok twice; (B) 1-2 acknowledged edits lost per 50; (C) PASS. The instrumented runs reproduce the same rate (35/60, 20/40, 20/40) with the cause located at the compare read inside the lock. S2-16 itself is unchanged and still FAIL.

Additional finding from the code, independent of timing: `restoreBackup` compares only the *backup* slot to `expectedRaw` (`storage.ts:334`) and reads `current` (331) without comparing it to any workspace baseline, so a restore can overwrite concurrent edits by design (a pre-restore snapshot is kept, 340-345). Not tested in a browser.

## 4. Options

**A. Repair the localStorage path.** Any fix remains a read of a value that Chromium may not yet show: possible tweaks are (i) hold the lock a few ms after every write (experiment above: 0/120), (ii) re-read after a settle delay, (iii) a cross-tab version handshake over BroadcastChannel. None gives a guarantee; (i) is a few lines in `withStorageLock`/`saveProjectsLocked` but cannot be proven correct, costs latency on every write, and the needed delay is host-dependent. The same weakness applies by construction to the other lock-plus-localStorage code (`durableStore.ts:95-103`, `cutoverController.ts`), which S2-02/S2-04 already show. Scope: small (≈20-60 lines + tests); backups/recovery unchanged; risk: false sense of safety.

**B. IndexedDB with compare-and-set in one transaction.** A `readwrite` transaction that reads the record, compares its version/raw to the expected value and `put`s the new one is serialised and isolated by the browser across tabs (the specified isolation guarantee, which localStorage does not provide), so the lost update is closed *by construction*. Scope (counted from the tree): rewrite `storage.ts` (404 lines) around an async store; `listBackups` is synchronous and used by `BackupManager.tsx:18` (becomes async); `App.tsx` (285) and `BackupManager.tsx` (114) adapt; `durableStore.ts` (470) and `cutoverController.ts` (399) currently take a `Storage` object and would need an IDB-backed port; ~11 test files use fake `Storage`, and no IDB test double is available offline here, so tests must run in real Chromium. Backup/recovery effect: backup slots and the pre-restore snapshot can be written in the **same transaction** as the workspace write (an improvement over the current non-atomic backup-then-write sequence, `storage.ts:209-211`), restore gets CAS on both the slot and the workspace, but all legacy backup keys/slots and the legacy workspace must be migrated once, which is exactly what PR-D's cutover does. New risks: IDB availability in private modes, eviction/quota policy (needs `navigator.storage.persist()` consideration), `versionchange`/blocked upgrades, transaction auto-commit pitfalls. **It does not solve R1:** pre-barrier tabs keep writing localStorage, which would no longer be read (silent loss of their edits instead of overwrite) unless the marker/revalidation detects it.

## 5. Recommendation

1. The root cause of S2-16 is established for Chromium 153: stale cross-tab `localStorage` reads inside the lock. A localStorage-based compare-and-set cannot be made strongly correct; do not rely on `expectedRaw` as a safety guarantee.
2. Prefer **B as the long-term fix**, designed together with PR-D (the durable stores and the cutover are the natural place for the backend change) rather than as a hot patch to the legacy path. It is a phase of its own (estimated order of magnitude: the ~2,600 lines of the storage/cutover/app files above are touched or wrapped, plus a real-browser test suite), needs owner approval, and must keep the S2-16 test as its acceptance test (expect 0 lost updates over many trials).
3. If something is needed sooner, A(i) can be offered **only** as an interim mitigation clearly labelled non-guaranteeing, validated with S2-16 at a much larger trial count, and with the S2-16 expectations unchanged.
4. Independently: record the `restoreBackup` workspace-overwrite finding, and decide whether the unreproduced timeout-race window deserves its own test.

## 6. Not done / limits
No production code or test expectation was changed; the hold-variant is a diagnostic wrapper in the script only. Not tested: other browsers, more than two tabs, the real React UI, `restoreBackup` concurrency in a browser, the timeout-race window, IndexedDB behaviour (no IDB prototype was built).

In neither mode was the new value visible at the instant `setItem` returned.

**What this adds.** (1) The cross-tab visibility delay is measurable without any DevMate code: the written value is not visible in another tab immediately, typically for about half a millisecond to a few milliseconds on this host. (2) It explains why S2-16 is host dependent: the lost update needs the lock hand-off gap to be shorter than the visibility delay. On this slower host the hand-off gap (1.1–3.2 ms) exceeded the typical delay and no stale compare read occurred in 60 trials; on the original host (gap 0–1.8 ms) it happened in 35 of 60. This is consistent with the lock-hold experiment in section 2 (hold ≥ 5 ms: 0/120). (3) The S2-04 unlocked control reaching 120 for an expected maximum of 90 (observed in my runs of PR #35's harness) is the same stale-read mechanism contaminating the control, so that control is not a clean baseline.

**Still not proven.** The internal Chromium mechanism (not instrumented); that the same delay distribution holds on the GitHub runner that produced the S2-04/S2-16 failures; any other browser; more than two tabs. The root cause statement in section 5.1 therefore stays at the strength originally given: established by observation for Chromium, not a guarantee, and `expectedRaw` must not be relied on as a safety guarantee.

**Recommendation unchanged.** Option B (IndexedDB compare-and-set in one transaction, designed with PR-D; see PR #37) remains the long-term fix and needs owner approval; A(i) is at most a labelled, non-guaranteeing interim. Live cutover remains prohibited and R1 is unaffected.
